- Flow per run: `POST /v1/auth/demo` -> `POST /v1/samples/{id}/import` -> `GET /v1/finance/home` + `GET /v1/next-move` -> judges `POST /v1/chat/stream` -> host `POST /v1/rooms {}` -> 3 players join over WebSocket -> all `ready` -> host `pick_game` same_life `{quick: true, quick_student_id, path_id}` -> `start` -> each player `POST /v1/lives {mode: random, start_year, seed: room.seed, room_code, path_id, quick: true}` -> AGE taps with random choices on every event, `progress` after each step, `finish` -> wait for `ranking` + `finished` -> `GET /v1/habits` + `GET /v1/finance/profile` (annual income).
- Judge 1 asks "Can I afford a night out this week?". Judge 2 asks "How much can I spend this week?".
- All times are client wall clock from London to Railway, in seconds. The round has no human think time, so round time is server time plus network.

## Verdict: FAIL

- Room, import, lobby, Quick Life, ranking, winner line and habits are green in all 5 runs.
- Two targets fail:
  - F1: Penny first bubble is over 3 s in 6 of 10 asks (owner W5 explain).

## Failures

### F1. Penny first bubble over 3 s (owner W5 explain; W4 for `chat_service.py` streaming)

- Slow asks (client s / server `elapsed_ms`): R1 judge1 3.81 / 3625; R2 judge2 9.72 / 9534; R3 judge2 6.71 / 6524; R4 judge1 7.31 / 7130; R4 judge2 9.96 / 9785; R5 judge2 7.98 / 7797.
- Server `elapsed_ms` matches client time, so the delay is in the server, not the network.
- No error events. Every answer has mode `checked` and `verified: true`. Every answer has 2 bubbles.
- Cause (follow-up probe, graduate, "How much can I spend this week?"): Penny calls `spend_prediction`, then `finance_summary`, then `next_move` in sequence. The first bubble comes at 7.5 s. A night-out question with one tool (`finance_summary`) gives the first bubble at 2.6 s.
- Wrong answer content in the same cases: "I can't give a weekly limit" and "I can only forecast a single day" (R2, R3, R4, R5 judge2). The app has a weekly budget (Next Move `weekly_budget` and the Money tab weekly budget). DIRECTION_V2 section 6 says Penny must never say she lacks data that the app has.
- Fix to request: route weekly-spend questions to the weekly budget tool first; run independent tools in parallel or stream the first bubble after the first tool; cap tool rounds before the first bubble.
- "Can I afford a night out this week?" is also variable: 2.25 to 3.81 s, and 7.31 s in R4.

### F2. Next Move card without sample size or confidence (owner W2 engine)

- `sample_size` is null on every `weekly_budget` move (R1 rich, R2 working, R3 loan_england), on `lifetime_isa` (R4 commuter) and on `build_emergency_fund` for scholarship (R1) and final_year (R4).
- `confidence_level` is null on `build_emergency_fund` for scholarship (R1) and final_year (R4).
- R4 commuter `lifetime_isa` has `confidence_level: "high"` with `sample_size: null`. DIRECTION_V2 section 8 bug 4: "High" only with a sufficient, relevant sample; show sample size.
- The section 5 card needs "confidence with sample size". These cards cannot show it.
- Trade-off and sources are present on all 20 cards (`decision_source_count` 5).

## Observations (not blocking)

- O1 (W5 or W4): the first `bubble` event arrives before the `verifying` event in 10 of 10 asks. The contract order is `reaction, tool_step*, verifying?, bubble+, done`. `done.verified` is true, so the numbers passed. Confirm that bubble 1 is verified before it is sent.
- O2 (W4): with `quick_student_id` set, `start` already creates a life for every player (`_create_quick_lives`). The client then calls `POST /v1/lives` with `room_code` (as the iOS `RoomFlowViewModel.startMyLife` does), which makes a second life per player. The first life stays as an orphan in the store. The round result is correct because `progress` switches `life_id`.
- O3 (W4): demo accounts have no display name, so the winner line says "Player 2 wins ...". On stage this is clear only if phones show the same "Player N" label. Names from onboarding fix this.
- O4: team1 and team2 have fixed habits (63 and 80) in every run, as expected for fixed sample data. The "lower income beats richer" moment depends on the judge picks. It held in runs 1, 3 and 4. For the stage, scholarship vs rich (run 1) gives the clearest gap: 82 vs 47.
- O5: winner line numbers match the ranking (INDEX) in all 5 runs. Ties use the habit score as the tie-break (R2, R5), or share the rank (R1).
- O6: no 429 from sign-in (20 sign-ins in about 2 minutes). No socket errors. No `error` WebSocket messages.
